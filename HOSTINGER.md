# Host Keymeter on Hostinger Business

Keymeter has a standalone production Node build with MySQL persistence and a private seller sign-in using an owner key and email verification code. Hostinger owner access does not require ChatGPT. The customer key checker can be public. The seller session is encrypted in the database. The Sites build remains available through the original build command.

## 1. Prepare the source

Push this Keymeter project to its own private GitHub repository, or upload a ZIP of this project with package.json at the top level. Exclude node_modules, dist, .git, outputs, .env files, local preview state, and runtime credentials. The older API_keyledger repository is a separate customer-management app.

Use Node 24 locally. Run `npm ci`, then `npm run hostinger:secrets`. Save the generated `SESSION_SECRET` and `BILLING_ENCRYPTION_KEY` in your password manager and private hPanel runtime settings. Set `ADMIN_EMAIL` to your fixed owner email before first setup. The website generates your 64-character owner key only after you verify that email; it shows the key once in the browser. No owner password prompt or owner key is generated by this command.

`ADMIN_PASSWORD_HASH` is optional compatibility configuration for an existing owner account that has no database key hash. Leave it blank for a fresh installation. Only use `npm run hostinger:secrets -- --legacy-password` when maintaining that legacy configuration; the hidden password prompt is retained for that case.

## 2. Create the Hostinger app

In hPanel, select Websites → Create site → Web App → Continue with GitHub and choose the Keymeter repository. A project ZIP is also supported. Choose the intended domain and use these settings.

| Setting | Value |
| --- | --- |
| Framework preset | Other |
| Node version | 24.x |
| Package manager | npm |
| Root directory | ./ |
| Build command | npm run build:hostinger |
| Output directory | dist |
| Entry file | server.mjs |
| Start command, if shown | npm run start:hostinger |
| Install command, if shown | npm ci --include=dev |

The build puts server.mjs at both the project root and output root. Hostinger can therefore use the same entry filename in either case. The app listens on PORT and all interfaces. Its internal production renderer listens only on loopback behind the authenticated gateway.

## 3. Create a MySQL database

Open the website's Dashboard → Databases → Management and create a new empty database and user. Copy the complete prefixed database name and username. Use DB_HOST=127.0.0.1 and DB_PORT=3306 for a database on the same Hostinger plan. Keep its password private and separate from the owner key.

Startup creates the app tables and records a schema checksum under a migration lock. A later restart reuses that schema. Preserve applied migration files. Use a dedicated Keymeter database.

## 4. Add runtime environment variables

At Review build settings → Environment variables, add the values below, or import a private copy of .env.example. Enter values without surrounding quotes in hPanel.

| Variable | Value |
| --- | --- |
| APP_URL | Exact HTTPS origin, for example https://keys.example.com |
| PORT | 3000, or the port Hostinger supplies |
| DB_HOST | 127.0.0.1 |
| DB_PORT | 3306 |
| DB_NAME | Full prefixed database name |
| DB_USER | Full prefixed username |
| DB_PASSWORD | Database password |
| ADMIN_EMAIL | Your fixed owner email; required before first setup |
| RESEND_API_KEY | Private Resend sending API key |
| AUTH_EMAIL_FROM | Sender on your verified Resend domain, for example Keymeter <auth@your-domain.com> |
| ADMIN_PASSWORD_HASH | Leave blank for fresh installs; optional legacy fallback only |
| SESSION_SECRET | Generated random session secret |
| BILLING_ENCRYPTION_KEY | Generated base64 encryption key |

The standalone runtime uses the gateway-verified owner ID. It ignores caller-supplied identity headers and supplies owner identity only after checking an authenticated session. The pinned email is verified during first setup and stored in the database with a key hash and account version. It can be changed later from Owner email & security after old- and new-email verification. For an existing account, the database email is authoritative; `ADMIN_EMAIL` pins fresh setup only. Keep the encryption key stable for this database. Changing `SESSION_SECRET` revokes owner sessions and pending verification proofs. Changing `ADMIN_PASSWORD_HASH` affects only accounts using the legacy fallback and proofs bound to it; it does not revoke sessions that use a database owner key. Key recovery or a completed email change rotates the account version and invalidates previous sessions.

For a fresh database, generate new secrets and reconnect RunningHub after deployment. Migrating the existing Sites database is a separate export and SQLite-to-MySQL conversion that must preserve its original encryption key. A SQLite dump cannot be imported directly into MySQL.

## 5. Deploy and connect RunningHub

Click Deploy. If the app shows “Keymeter setup is incomplete,” add or correct the required environment settings and restart it. Runtime logs report configuration names without showing secret values.

Open `https://YOUR-DOMAIN/login`. For a fresh installation, the fixed owner email from `ADMIN_EMAIL` is shown. Click **Send setup code**, then enter the six-digit code delivered to that address. The website creates a random 64-character owner key and displays it once. Save it in your password manager before continuing; only its salted hash is stored in the database. Later sign-ins require the current owner email, owner key, and a fresh emailed code. Select Remember this browser for a seven-day authenticated session; otherwise the session lasts eight hours. Setup and key recovery create an eight-hour session. Email codes are never printed in logs, returned in the website response, or placed in URLs. Open `/seller` and connect your RunningHub seller session there. Include the optional Rh-Refreshtoken once for automatic renewal, or use the refresh-only form after connecting. An already saved access token does not need to be pasted again for this step. Every shared key from that connected account is available automatically. Customers enter their own full issued key on the home page to see its allowance and job charges.

Compare one key's results against RunningHub's billing console before sharing the customer URL. RunningHub website sessions can expire, and its internal billing endpoints can change. Reconnect from /seller if the site requests it. The deployed code's available renewal behavior is described on the seller page.

## 6. Configure owner email delivery

Create a Resend account and verify a domain or subdomain you own using the DNS records Resend provides. Set a sending API key as RESEND_API_KEY and an address on that verified domain as AUTH_EMAIL_FROM in private hPanel environment settings. Restart the app after configuring these values. There is no SMTP dependency or ChatGPT login in the standalone gateway.

Missing email settings or a mail-provider failure blocks first setup, key recovery, and new owner sign-ins. It never skips the email-code stage, disconnects RunningHub, or invalidates an already authenticated browser. The public checker can still run when owner email delivery has not yet been configured. Actual delivery and inbox placement must be verified after deployment with your configured provider.

Owner sign-in forms work in embedded browsers using a signed hidden form proof and an HttpOnly cookie. If a form expires, reload `/login` and submit the fresh form. Cookies must be enabled. A foreign-origin submission remains blocked; keep `APP_URL` equal to the exact HTTPS address you use to visit the site, without a path. Email-code verification is still required.

Codes expire after five minutes, allow five incorrect attempts, and can be used once. A resend waits at least sixty seconds for that browser and supersedes its previous code. A separate aggregate budget allows at most three emails in a minute and ten in an hour. Only random pre-authentication cookies and keyed code hashes are stored; the code is sent to the email being verified and never placed in a URL.

To change the owner email, open /owner/email from the authenticated billing settings. Enter the current owner key and the new address, then verify a code at the old address and another at the new one. The address changes only after both codes succeed. Other signed-in browsers are signed out, and pending codes are invalidated. Sign out is also available on that page. If you lose the owner key, choose **Forgot key** at `/login`, enter the current owner email, and verify the recovery code. A replacement 64-character key is shown once. The old key, signed-in sessions, and pending codes stop working; your encrypted RunningHub connection and billing data remain saved. Recovery does not bypass email verification. Lost access to the owner mailbox requires operator-assisted recovery that preserves `billing_connection` and `BILLING_ENCRYPTION_KEY`.

## 7. Verify and maintain

Check the home page in a signed-out browser, then open /seller and confirm it requires owner sign-in. The seller API should reject unsigned requests even if they include fabricated oai-authenticated-user headers. Check a real key and confirm the intended currency, remaining allowance, and job charges. Keep Hostinger backups enabled for the database and store the encryption key separately with those backups.

Owner sign-in runs at most two password hashes concurrently. Short ten-second buckets allow six attempts for a username and socket peer, with a separate twenty-attempt global budget. Busy responses include Retry-After; the limiter does not invalidate existing owner sessions. A sustained attack can still saturate a public login while it continues. Keep the generated owner key private in a password manager.

The gateway deliberately trusts only its socket peer for IP rate limits. Hostinger's reverse proxy may therefore combine customer traffic into one sixty-checks-per-minute allowance bucket, alongside the thirty-checks-per-minute limit for each key. Caller-supplied forwarded-IP headers are ignored. Treat that as a conservative aggregate budget until Hostinger's trusted proxy identity behavior is verified; do not enable arbitrary forwarded-header trust to increase it.

Deploy later changes from the repository. Restart after changing environment settings. Monitor Hostinger Runtime logs for bounded error messages. Billing failures and a disconnected provider are shown explicitly in the UI.

Local checks are npm run test:hostinger and npm run build:hostinger. The test suite uses synthetic credentials and local test servers. A production MySQL smoke check still requires an isolated test database; do not run integration tests against customer data.
