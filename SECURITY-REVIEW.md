# Keymeter security review

This implementation review covers customer key isolation, seller access, stored sessions, request handling, pricing administration, dependencies, and the Hostinger adapter. It combines source review with automated checks. It is not a formal penetration test or security certification.

## Protections and validation

- Customer keys are authenticated with RunningHub. The complete authenticated key roster is checked against the connected seller account before billing records are selected. Ambiguous identities and mismatched records fail closed.
- The Sites build retains verified ChatGPT owner identity plus a separate billing password. Its password uses salted native scrypt (N=32768, r=8, p=3) with a domain-separated server-secret pepper. First setup is atomic and owner-only. Random unlock cookies last eight hours and are bound to the owner and password version; only keyed hashes are stored. Locking billing removes the unlock session without disconnecting RunningHub.
- The Hostinger build uses independent owner-key-and-email-code authentication at `/login`, without a ChatGPT account. Fresh setup is pinned to the privately configured `ADMIN_EMAIL`. Verifying its setup code atomically claims the singleton account and generates a random 64-character key with uppercase, lowercase, digits, and symbols. The raw key is shown once in the browser; only its salted scrypt hash is stored. Key recovery verifies the current owner email, replaces the hash and account version, and revokes previous keys, sessions, and pending codes without clearing the encrypted RunningHub connection. Later email changes require an authenticated session, the current owner key, a code sent to the old email, and a second code sent to the new email. The final version-checked update invalidates old sessions and pending codes.
- Hostinger email codes are random, single-use, valid for five minutes, and limited to five verification attempts. Only keyed code and challenge hashes are stored. Challenges bind the owner email/version, purpose, and proposed new email; login proof cannot become email-change proof. Resends replace old browser challenges and have a 60-second cooldown, with bounded global send budgets and short password-attempt limits. Mail requests use a fixed HTTPS Resend endpoint, timeouts, redirect rejection, and bounded response parsing. Email codes and stored credentials are not logged or returned to the browser. The newly generated owner key is the explicit exception: it is shown once after successful setup or recovery, with no-store response headers.
- Owner session cookies are opaque, HttpOnly, SameSite=Strict, and Secure on HTTPS. Hostinger sessions last eight hours, or seven days when the owner chooses to remember the browser after successful code verification. Keyed session hashes bind the current database owner email/version, effective database key hash (or legacy fallback hash), and session secret. Rotating `SESSION_SECRET` invalidates all owner sessions. An environment `ADMIN_PASSWORD_HASH` change affects only legacy fallback accounts and associated proofs; database-key sessions do not depend on that fallback. The gateway strips public identity and forwarding headers. It verifies the owner session before passing owner identity and a process-local proof to the renderer. The runtime's fixed owner ID lets a verified email change work without changing an environment variable or restarting.
- All Hostinger authentication forms, including setup, key recovery, resend, logout, and email changes, require an HMAC-signed hidden proof bound to an independent HttpOnly browser cookie, the configured site origin, and the current authentication/pre-authentication cookies. Proofs expire after one hour. Explicit foreign origins, missing or duplicate proofs/cookies, tampering, and session changes are rejected. Embedded-browser submissions with missing or opaque `Origin` headers require the same signed proof; matching headers alone never authorize a form. Errors render a fresh sign-in form rather than a bare rejection. The seller JSON APIs retain their separate origin checks.
- Seller credentials are encrypted with AES-GCM in the database. Preserve the server encryption key across deployments and database restores. Customer responses, application logs, and source control exclude raw customer keys and seller tokens.
- Requests have bounded bodies, fixed upstream destinations, timeouts, origin checks, response field filtering, and database-backed throttling. Sensitive responses use no-store caching directives.
- Session renewal uses a short database lock and ciphertext compare-and-swap. Application tests cover concurrent renewal, manual reconnect/disconnect, transient outages, currency handling, owner access, password cookies, CSRF, body limits, setup races, and expiration. The latest application suite passed 34 tests. Hostinger integration also passed against a disposable MariaDB instance and the compiled production server, exercising pinned-email setup, generated-key setup/recovery and rotation, email changes, replay/expiry/attempt limits, protected pricing writes, and public pricing persistence. Synthetic email delivery was injected in automated tests; those tests sent no real email. A separate local browser-bound setup request was accepted by the real Resend service; mailbox receipt and owner verification remain pending.
- Customers can read advertised prices, but pricing changes require the authenticated owner gateway or the verified Sites owner plus password unlock. The pricing API enforces same-origin writes, JSON/body bounds, request limits, exactly six supported USD packages, and bounded whole-number Ks prices. Values are validated before database storage. Contact links do not include the submitted customer API key.

## Connection and deployment limits

- An access-only RunningHub session remains saved across visits and deployments. Automatic renewal requires the optional refresh token to be supplied once through owner setup. It can be attached without re-entering the saved access token. Redeemed credentials must identify the same provider-authenticated account; foreign subjects, rosters, and currencies fail closed. A previously validated encrypted subject supports refresh-only recovery after access expiry when RunningHub authenticates a matching replacement. Provider expiry, revocation, or rotation in another browser can still require reconnection.
- Email delivery is implemented but requires private `RESEND_API_KEY` and `AUTH_EMAIL_FROM` settings and a verified sending domain. Missing mail configuration or a delivery outage blocks first setup, recovery, and new owner code delivery; it does not bypass the code step, revoke existing owner sessions, or take the public checker offline. Real delivery to the owner's mailbox has not been verified.
- The production dependency audit reported zero known vulnerabilities. The full audit retains 21 development-tool findings: 20 moderate and one low, with none high or critical in that audit.
- Trusted Hostinger proxy metadata has not been verified. Customers behind the same proxy can share an address-based request-limit bucket. Deployment on an actual Hostinger account remains unverified.
- Sites publication is currently blocked because the connected Sites account cannot find the existing project. The correct local Hostinger preview serves the standalone gateway; `npm run dev` serves the separate Sites authentication path. Local automated checks and production builds do not establish that the new release is live.

## Access and recovery

For Sites, open `/seller` with the verified Site owner account and choose the billing password privately. If it is lost, the deployment operator must remove only `seller_password` and `seller_sessions` rows through authenticated database administration before owner setup can be repeated.

For fresh Hostinger setup, privately pin `ADMIN_EMAIL` and configure the verified email sender before opening `/login`. Verify the setup code and save the 64-character owner key displayed once. Later login requires that key plus a delivered email code. The public **Forgot key** flow sends recovery proof only to the current owner email and displays a new key once after verification. It revokes the old key and sessions while preserving `billing_connection` and `BILLING_ENCRYPTION_KEY`. Email changes use the protected owner-email settings. No lost-mailbox bypass is provided. `ADMIN_PASSWORD_HASH` remains optional compatibility configuration only for an older account whose database key hash is null; fresh installs leave it blank.

The Sites password work factor follows an [OWASP scrypt parameter option](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). The Worker uses [documented native Node crypto support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/) with `nodejs_compat`. Email setup follows Resend's [verified-domain requirements](https://resend.com/docs/dashboard/domains/introduction) and [send-email API](https://resend.com/docs/api-reference/emails/send-email).

The Hostinger form checks use the session-bound HMAC pattern described in [OWASP CSRF prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#signed-double-submit-cookie-recommended). Regression tests cover missing/null browser origin headers, cookie and token tampering/expiry, foreign origins with valid proofs, all authentication POST routes, and complete owner-key/code flows through the gateway. Both Hostinger test suites and the compiled production-entry checks passed. The local preview uses an isolated persistent database and loopback-only app/database listeners. Its private configuration does not inherit production mail credentials; actual email delivery remains blocked until configured privately. No real verification email has been sent as part of these automated checks.
