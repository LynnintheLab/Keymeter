# Build Keymeter

Build and test a mobile-friendly website where a customer can paste the full international RunningHub Enterprise-Shared API key they bought and check how much of **that key's spending allowance** remains. The customer needs one screen, one field, and one action. Name the site **Keymeter**. Deliver the working frontend, a same-origin server endpoint, and setup and verification instructions.

## Customer experience

- Lead with “How much is left on your key?” Label the masked input “Enterprise-Shared API key”. Include a keyboard-accessible Show/Hide button, disable autocomplete and spellcheck, and label the submit button “Check allowance”.
- On success, make the remaining allowance the largest figure. Show the key limit, usage, last four characters, and check time. Format verified international USD amounts with enough decimal places to preserve fractional usage. Clearly flag an expired or exhausted key.
- Use a quiet, high-contrast layout with the form beside a receipt-style statement on desktop and above it on a phone. A small gauge may accompany a known cap. Give the gauge a text equivalent. Use visible focus indicators and announce loading, results, and errors to assistive technology.
- Before the first lookup, show the key field and action without example balances. Clear previous figures when the input changes or another lookup starts. During loading or after any failure, show no amount, percentage, sample balance, or previous customer's result. Offer a retry for temporary failures. Clear the key after success and keep it masked while checking.
- Keep the check manual and read-only. Keep history scoped to the verified key. Omit account creation, reminders, notifications, and model or job execution.

## Provider lookup and arithmetic

1. Have the browser send the full key in a JSON body to a same-origin HTTPS POST endpoint such as `/api/allowance`. Validate the input on the server. Reject empty, masked, malformed, and oversized inputs before contacting the provider.
2. Verify RunningHub's current regional documentation and field semantics before enabling production lookups. A candidate for the international host is `GET https://www.runninghub.ai/openapi/v2/api-key/list` with Bearer authentication. The [list reference](https://www.runninghub.cn/runninghub-api-doc-cn/api-432924538) describes the China-host route and is marked in development. Compatibility with the international host, USD units, masking, and shared-key permissions require a live check.
3. Authorize the request with the submitted key when its permissions allow lookup. Require a successful provider envelope and identify exactly one row belonging to that key. Prefer exact full-key identity. Accept a provider-masked identity only when its mask format is verified, the full submitted key has been authenticated or enrolled, and exactly one row matches the exposed prefix and suffix across the complete applicable result set. Fail closed on missing, ambiguous, or incomplete matches. Never choose the first row or match by suffix alone.
4. Read `quotaLimit` and `quotaUsed` from that row. Compute `remaining = max(0, quotaLimit − quotaUsed)` using decimal-safe arithmetic. Preserve a zero cap. For an explicitly null cap, display “No limit reported” and known usage. A missing field, unexpected unit, invalid amount, or malformed payload makes the lookup unavailable. Show expiration separately from the arithmetic. Avoid promises that a job will run. The shared account wallet is outside the scope of the checker.

## Actual job usage history

Show each actual job's date/time, model or workflow name, status, task ID, and final billed charge. Fetch the most recent 50 records in the last 30 days from the seller account when the customer checks their key. Set up an owner-only seller page. The seller connects a RunningHub website session, and every current and future shared key becomes available automatically after provider authentication and a complete account-roster identity match. Encrypt the owner connection server-side. Decrypt it only for fixed RunningHub billing query routes after authorizing the request. Never allow customer input to choose the provider key ID. Filter every returned row against the server-verified provider key ID and handle grouped child tasks without inventing or double-counting charges. Use the reported currency and retain decimal precision. Show connection/setup/expiry failures clearly. Explain that the website integration may need updates as RunningHub changes its internal endpoints. Keep access and optional refresh tokens encrypted, renew with a database concurrency lock, preserve the connection across visits and deployments, and show actual expiry/revocation conditions. Add atomic request limits and an independent secure owner login for Hostinger. Require a real owner-console comparison before marking automatic billing verified.

## Balance checks

Show the latest 30 successful checks for each key. Record the check time, total used, and remaining allowance in a server database. After verifying the key with RunningHub, select readings by a one-way fingerprint of the entire key. Calculate changes using integer microdollars and chronological order. Label the first entry as the starting reading. Show decreases as decreases in reported usage. Explain that the time is when the key was checked. For individual job charges give the seller a link to RunningHub Tasks & Billing where they can filter by key. Hide the previous key’s history during a new lookup. If the database is unavailable, keep the verified current allowance visible and mark history unavailable.

## Privacy and optional seller-assisted access

- Pin the upstream origin and route on the server. On Cloudflare Workers use redirect: 'manual' and reject all 3xx responses; never follow a redirect with the key. Bound request and response sizes, set a timeout, and limit abusive traffic. Use `Cache-Control: no-store` for every success and error. Use generic, actionable messages for denied access, throttling, provider failures, and network interruptions.
- Serialize only the matched key's limit, used amount, remaining amount, normalized state, suffix, check time, and that key’s recorded readings. Keep the full key, raw provider payloads, sibling rows, account details, names, and upstream errors out of customer responses. Disable body/header capture, session replay, and secret-bearing logs. Never write submitted keys to storage, URLs, analytics, source control, or test artifacts.
- If shared keys lack list permission, support an optional owner-assisted lookup. Keep a least-privilege authorized owner credential and an allowlist of SHA-256 fingerprints of the exact sold keys in server-side runtime secrets, for example `RUNNINGHUB_OWNER_KEY` and `REGISTERED_KEY_HASHES`. Use the owner credential only after the full submitted key's fingerprint matches an explicit enrollment. Disable owner-assisted access if either secret is absent. Always match the result against the customer's key. Document enrollment, rotation, and revocation. Use placeholders in setup instructions and synthetic credentials in tests. The owner enters secrets privately in their hosting dashboard.

## Deployment and acceptance

Provide the actual install, build, test, and start commands for the chosen stack. Document how to configure HTTPS, server-side secrets, and customer access on the target host. For Hostinger, specify the required server runtime and how the frontend reaches its backend. Verify the deployed POST route through the same public origin customers will use.

- Test with synthetic responses covering two distinct customers, masked-key collisions, missing fields, zero and null caps, fractional usage, overspend, and expiry. Prove that an unenrolled submission cannot trigger the owner credential. Inspect the response field allowlist and cache headers.
- Exercise the deployed UI on a phone-sized viewport. Submit an invalid key, then simulate denial, throttling, and a network interruption after a successful lookup. Confirm the old figures disappear, no sample figures appear, and retry works. Check that reload forgets the key.
- Have the owner privately check an authorized real shared key against its matching console row on the deployed site. Compare the cap, used amount, remaining amount, and currency. Record pass/fail without a credential, raw response, or identifiable screenshot. State which tests used fixtures, which ran on the deployed site, and whether the real provider comparison passed or is still pending.


## Current UI and owner access requirements

Use a compact dark navy technical interface with restrained green actions, monospace key/data labels, fine borders, and a static low-contrast dot background. Remove example balances and sample figures entirely. Initial state contains only a key input, one check action, and brief help. Show real remaining allowance, limit, usage, and per-job charges only after a successful lookup. Keep secondary help and saved readings collapsed. Preserve mobile layout, accessible labels and errors, keyboard focus, and reduced-motion behavior.

On Sites, require verified owner identity plus a privately chosen billing password on both the seller page and every seller API operation. Use a supported slow password hash with random salt and server-secret pepper, atomic first setup, bounded verification concurrency, short rate limits, and opaque secure HttpOnly session cookies bound to the owner and password version. Locking the billing page must not disconnect RunningHub. Standalone Hostinger uses its independent owner-key/email-code gateway and does not duplicate the Sites password.

Allow an owner to attach a refresh token once without re-entering the saved access token. Authenticate the rotated access token with RunningHub, prove account continuity from the saved validated identity and roster, verify team/currency, and persist it encrypted with a compare-and-swap lock. Invalid, foreign, or transiently failed refresh attempts preserve the original connection. Do not claim provider login lasts forever; revocation or provider changes can still require reconnection.
